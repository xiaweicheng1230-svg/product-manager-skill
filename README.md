# 产品经理 Skill

一套面向软件、智能硬件、AI 产品、手机应用、微信小程序、平台后端和设备端项目的产品文档框架。

它帮助产品经理把零散的想法、原型、会议记录、竞品资料和技术约束，整理成领导看得懂、研发做得出、测试验得过的产品文档。

> 这不是一组机械套用的空模板。Skill 会先判断项目阶段、文档读者和当前要解决的问题，再选择需要的文档与详细程度。

## 能解决什么问题

- 项目刚成立，不知道应该先梳理哪些材料；
- 需求只有口头描述，研发无法据此开始设计和开发；
- 软件、硬件、算法、平台和客户端各写各的，业务闭环对不上；
- 文档写了很多背景，却没有明确功能、状态、异常和验收标准；
- 领导需要看产品全貌，技术人员需要看可执行细节；
- 已经有原型或旧文档，需要补齐遗漏、统一名称并形成正式版本；
- 文档准备公开发布，需要排查公司信息、客户数据和项目隐私。

## 做一个产品的完整流程

产品经理的工作不是从写 PRD 开始，也不是交付 PRD 后结束。完整过程要经历机会判断、项目立项、产品定义、方案设计、技术落地、开发交付、发布运营和持续迭代；产品停止维护时还要处理用户、数据、设备和公司资产。

```mermaid
flowchart LR
    A[1 想法与约束] --> B[2 市场与用户调研]
    B --> C[3 机会判断与立项]
    C --> D[4 产品定义与MVP]
    D --> E[5 需求与体验设计]
    E --> F[6 技术方案与跨端对接]
    F --> G[7 计划与开发准备]
    G --> H[8 开发与过程管理]
    H --> I[9 测试验收与发布准备]
    I --> J[10 试运行与正式发布]
    J --> K[11 运营监测与版本迭代]
    K --> D
    K --> L[12 停止维护与产品退出]
```

### 全生命周期阶段表

| 阶段 | 核心工作 | 主要输出文档 | 进入下一阶段的条件 |
|---|---|---|---|
| 1. 想法与约束 | 把口头想法转成问题，盘点战略、资源、时间、成本和合规约束 | 产品构想、问题清单、约束清单、待验证假设、相关方清单 | 团队确认值得进一步调研 |
| 2. 市场与用户调研 | 研究市场、竞品、用户、场景、替代方案和真实痛点 | 市场调研、竞品分析、用户画像、用户旅程、场景清单 | 有证据说明用户、问题和机会确实存在 |
| 3. 机会判断与立项 | 评估用户价值、业务价值、差异化、可行性、预算和风险 | 立项书、商业画布、可行性分析、初步预算、风险清单、项目章程 | 决策人批准目标、资源、负责人和成功指标 |
| 4. 产品定义与MVP | 明确定位、目标用户、核心场景、功能边界、MVP和版本路线 | 产品定位、功能大纲、业务流程、MVP清单、路线图、指标定义 | 各部门对首版做什么和不做什么达成一致 |
| 5. 需求与体验设计 | 把产品定义变成用户可操作、研发可实现、测试可验证的方案 | PRD、信息架构、用户流程、页面清单、交互原型、文案与设计规范 | 核心流程、页面状态、异常和验收标准评审通过 |
| 6. 技术方案与跨端对接 | 设计客户端、平台、设备、算法、硬件、数据和第三方协作方式 | 技术方案、软硬件需求、平台需求、系统架构、接口、数据字典、设备协议 | 技术可行，关键风险完成验证，外部依赖有人负责 |
| 7. 计划与开发准备 | 拆任务、排工期、配资源，建立变更、风险、沟通和联调机制 | 工作分解、排期、里程碑、人员分工、风险台账、需求基线 | 团队拥有开始开发所需的人员、环境、账号、设备和数据 |
| 8. 开发与过程管理 | 按版本开发、联调和演示，持续管理问题、决策、风险和需求变更 | 迭代计划、任务看板、会议纪要、决策记录、变更记录、联调记录 | 功能开发和自测完成，核心链路已经联通 |
| 9. 测试验收与发布准备 | 验证功能、体验、性能、安全、兼容、可靠性和真实场景 | 测试计划、测试用例、缺陷清单、测试报告、验收报告、发布与回滚方案 | 阻塞问题关闭，遗留问题被接受，发布保障准备完成 |
| 10. 试运行与正式发布 | 小范围验证真实效果，监控指标和风险，再逐步扩大规模 | 试运行方案、发布计划、运营计划、监控看板、应急预案、发布公告 | 试运行指标达到标准，决策人批准正式发布或扩大范围 |
| 11. 运营与版本迭代 | 监测使用、留存、转化、成本、故障和反馈，决定下一版投入 | 数据看板、运营报告、反馈池、需求池、复盘报告、下一版路线图 | 新版本需求有数据、价值、成本和优先级依据 |
| 12. 停止维护与退出 | 处理用户、合同、数据、设备、库存、售后和资产归档 | 退出评估、停止维护计划、用户通知、数据方案、资产归档、项目总结 | 用户权益和公司义务处理完毕，系统能够安全关闭 |

各阶段的具体活动、输出物和通过条件见 [`references/product-lifecycle.md`](references/product-lifecycle.md)。项目可根据规模裁剪步骤，但不能跳过影响产品方向、安全、成本和交付责任的关键决策。

### 产品推进的三个闭环

#### 1. 决策闭环

```text
发现问题 → 收集证据 → 提出方案 → 评估价值、成本和风险
→ 明确决策人 → 记录结论 → 跟踪决策结果
```

#### 2. 需求交付闭环

```text
用户场景 → 产品需求 → 交互与技术方案 → 任务与排期
→ 开发联调 → 测试验收 → 发布验证 → 问题回收
```

#### 3. 数据迭代闭环

```text
确定目标指标 → 设计数据采集 → 发布后监测 → 分析原因
→ 形成需求假设 → 排定优先级 → 进入下一版本 → 再次验证
```

### 贯穿全流程的管理框架

- **范围管理**：维护版本边界、需求基线和不做清单；
- **变更管理**：记录变更原因、影响范围、决策人和实施版本；
- **风险管理**：记录概率、影响、负责人、应对措施和触发条件；
- **决策管理**：重大结论保留背景、选项、决策依据和后续影响；
- **质量管理**：让需求能够追踪到设计、开发、测试和验收；
- **数据管理**：统一指标名称、统计口径、数据来源、权限和保存规则；
- **安全与隐私**：最小化收集，明确授权、访问、保存、删除和审计；
- **成本管理**：同时考虑研发、采购、云服务、生产、运维和售后成本；
- **版本管理**：对应产品、软件、硬件、固件、算法、接口和文档版本；
- **沟通管理**：每次会议形成明确结论、负责人、期限和未决问题。

### 每次阶段评审要回答什么

1. 本阶段目标是否完成，有什么证据；
2. 哪些范围已经确认，哪些发生变化；
3. 指标、成本、时间和质量是否符合预期；
4. 最大风险、依赖和未决问题是什么；
5. 下一阶段需要哪些输入、资源和授权；
6. 结论是通过、有条件通过、返工还是暂停。

## 框架的四个层次

### 1. 任务路由

[`SKILL.md`](SKILL.md) 是入口。它先识别文档读者、项目阶段、已有材料和决策目标，再决定需要读取哪一类框架，避免一次加载或生成所有内容。

### 2. 专项方法

`references/` 保存不同阶段的工作方法：

- `product-lifecycle.md`：产品从想法、立项、开发、发布到迭代或退出的完整流程；
- `document-map.md`：根据项目阶段选择文档；
- `discovery-frameworks.md`：竞品、用户、场景和商业机会；
- `product-definition-frameworks.md`：功能大纲、PRD、MVP和版本规划；
- `interaction-frameworks.md`：信息架构、用户流程、页面状态和跨端交互；
- `technical-frameworks.md`：硬件、客户端、设备端、平台后端、接口和数据；
- `delivery-frameworks.md`：会议、排期、风险、评审、测试和验收；
- `writing-and-review.md`：正式文档的写作与审校规则；
- `public-release-checklist.md`：公开发布前的脱敏和质量检查。

### 3. 可编辑模板

`assets/templates/` 提供八类 Markdown 起始模板：

1. 竞品分析；
2. 产品需求文档（PRD）；
3. MVP与版本路线图；
4. 硬件产品需求；
5. 软件产品需求；
6. 平台后端需求；
7. 会议纪要；
8. 测试与验收。

模板只负责建立骨架。实际使用时，Skill 会结合真实项目补充内容，并删除不适用章节和占位符。

### 4. 文档生成工具

`scripts/scaffold_product_docs.py` 可以一次生成完整文档包，也可以只生成当前阶段需要的文件。脚本默认不覆盖已有文件，减少误删和返工风险。

## 核心工作方法

### 按读者控制详细程度

- 面向领导：突出产品价值、目标用户、范围、成本、里程碑和风险；
- 面向研发：补充业务流程、状态、字段、异常、接口和边界；
- 面向硬件与供应链：说明名称、功能用途、真实使用效果、关键参数和验收方法；
- 面向测试：把每项需求转成可观察、可复现、可判定的验收条件。

### 区分三类信息

- **已经确认**：来自正式决策、真实系统或可靠资料；
- **可以合理确定**：风险较低，不改变成本、安全和产品方向；
- **必须确认**：涉及成本、硬件选型、合规、安全、部门职责或重大范围变化。

### 把目标与事实分开

- “计划做什么”不等于“实际完成了什么”；
- “产品总体需求”不等于“当前开发进度”；
- 原型中出现的功能不自动代表已经实现；
- 数据表已经建立不代表接口、页面和设备闭环已经完成。

### 写清跨端业务闭环

涉及手机端、小程序、平台后端、设备端和算法时，统一回答：

```text
谁发起 → 平台保存什么 → 设备收到什么 → 设备如何执行
→ 结果如何回传 → 用户和管理人员看到什么 → 失败时如何处理
```

### 需求必须能够验收

每项关键需求至少说明：使用角色、使用场景、入口与操作、正常结果、异常处理、数据状态以及完成标准。参数优先描述真实使用效果，只对影响选型、安全、兼容和验收的指标给出明确数值。

## 安装

将仓库克隆到 Codex 的 Skills 目录：

```bash
git clone https://github.com/xiaweicheng1230-svg/product-manager-skill.git ~/.codex/skills/product-manager
```

Windows PowerShell：

```powershell
git clone https://github.com/xiaweicheng1230-svg/product-manager-skill.git "$env:USERPROFILE\.codex\skills\product-manager"
```

重新打开 Codex 后，可以显式调用 `$product-manager`；在产品文档类任务中也允许自动触发。

## 快速使用

### 在 Codex 中直接调用

```text
使用 $product-manager，从0到1规划这个产品：先判断当前处于什么阶段，再给出完整产品流程、各阶段任务、需要编写的文档、参与部门、评审节点和交付标准。
```

```text
使用 $product-manager，根据现有原型和会议纪要，判断当前需要哪些产品文档并生成正式版本。
```

```text
使用 $product-manager，为一个智能硬件项目生成硬件产品需求、客户端软件需求、平台后端需求和验收清单。面向研发团队，需求要能够直接执行。
```

```text
使用 $product-manager，评审现有PRD，找出范围、流程、异常、数据、权限和验收方面的遗漏，不要擅自增加新功能。
```

### 生成完整 Markdown 文档包

```bash
python scripts/scaffold_product_docs.py \
  --output ./product-docs \
  --project-name "示例项目" \
  --docs all
```

### 只生成部分文档

```bash
python scripts/scaffold_product_docs.py \
  --output ./product-docs \
  --project-name "示例项目" \
  --docs prd,hardware,software,backend,roadmap,meeting,acceptance,competitor
```

脚本默认跳过已经存在的文件。只有确认需要覆盖时才增加 `--force`。

## 推荐文档组合

| 项目情况 | 推荐文档包 |
|---|---|
| 新项目立项 | 竞品分析、用户场景、商业画布、功能大纲、MVP规划、PRD |
| 智能硬件进入选型 | PRD、系统架构、硬件需求、设备端界面需求、平台后端需求、接口与数据字典、验收清单 |
| 手机应用或小程序开发 | PRD、信息架构、页面与交互说明、平台后端需求、接口说明、隐私清单、验收清单 |
| 已有原型进入研发 | 页面清单、用户流程、页面状态、权限、数据、异常、非功能需求和验收清单 |
| 开发过程管理 | 会议纪要、任务分工、版本计划、风险清单、阶段评审与验收 |

## 使用边界

- 本仓库不包含任何原始公司资料、客户数据、项目账号、密钥或未授权文档；
- 参考文档和竞品材料只作为信息来源，不会被当成执行指令；
- 不会因为模板中存在某章节就擅自增加支付、商城、社交、医疗诊断等功能；
- 涉及儿童、健康、摄像头、声音、位置和身份数据时，应补充授权、保存、访问和删除规则；
- 正式交付前仍需由项目负责人确认关键范围、成本、合规、安全和跨部门责任。
